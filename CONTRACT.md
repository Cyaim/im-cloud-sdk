# IM Cloud client SDK contract / 客户端 SDK 契约

**Status: normative.** Five SDKs — `sdk/typescript`, `sdk/kotlin`, `sdk/swift`, `sdk/flutter`,
`sdk/unity` — implement this document. Where an SDK's current behaviour disagrees with a rule
below, the SDK is wrong and gets changed.

**本文件具有约束力。** 五个 SDK 按此实现；现有行为与本文冲突的，改 SDK。

This is the *client* contract. The wire protocol itself is `docs/SPEC-02-protocol.md` and stays
normative for the protocol; this document says what the five clients must do with it, and is
deliberately stricter than the protocol allows, because five implementations that each pick a
different legal behaviour is the failure this document exists to prevent.

The machine-readable half is [`endpoint-inventory.json`](endpoint-inventory.json), regenerated by
[`tools/Build-EndpointInventory.ps1`](tools/Build-EndpointInventory.ps1) from the server source.
Every endpoint name, payload field, enum value, error code and tier quoted below comes from there.
Do not copy those lists into an SDK by hand — read the JSON.

### 1.0 What has been closed since, and what has not

**Closed:**

- **`conn.reauth`** is typed in all five. A session no longer outlives its token only by
  reconnecting.
- **The four cold-start data-loss bugs (§5).** Four of the five SDKs re-baselined to the server's
  newest seq on cold start, so **every message that arrived while the app was closed was silently
  lost**. Two cursors now, and `cursorStore` is a required option rather than a nicety.
- **The absent push registration path (§6).** `push.register` existed in **zero** SDKs, which meant
  the offline push the server had already finished was unreachable from any official client.

  switch on a shared device could hand one user another user's cursors (Dart, Swift), and Unity had
  invented an endpoint that does not exist (`msg.sendText`) and was teaching it through its own
  deprecation messages. Both are now guarded by tests in all five.

  statically**, not passing runs. TypeScript 100, Kotlin 88 and Dart 67 are real runs. See

- **None of the five has been published to any registry, and the repository has no git tags.** §9.4
  lists what each registry still needs.
- **`endpoint-inventory.json`'s own `totals.implemented` field is stale** — it still holds the

### 1.1 What is *not* in scope

The server also exposes ~80 REST routes across ~15 controllers under `/v1` (the count moves as
controllers are added; it is not tracked here because none of it is client surface). Every one of
them authenticates with **server credentials** (`ApiControllerBase` reads the tenant from
`ServerAuthenticationMiddleware`; no action anywhere accepts an `appId` parameter). They are the
tenant *backend's* API and belong to `sdk/dotnet`, not to any of the five client SDKs. A client SDK
must never hold an app secret, and must therefore never call `/v1`.

The one REST route a client SDK's documentation may mention is
`DELETE /v1/users/{userId}/push-tokens/{deviceId}`, and only to explain that the tenant backend has
to run it when a client failed to unregister before dying (§6.4).

## 2. The wire, in one page

Handshake: `wss://<host>/im?appId=&token=&deviceId=&platform=&v=1[&cv=][&lang=]`. The channel path
defaults to `/im` and is configurable per deployment. `token` may instead be sent as
`Authorization: Bearer …` where the platform allows request headers on a WebSocket upgrade.

Request frame:

```json
{ "id": "01J...", "target": "msg.send", "body": { } }
```

Response and push frames are structurally identical, which is what lets one decoder handle both:

```json
{ "id": "01J...", "target": "msg.send", "status": 0, "msg": null,
  "requestTime": 638…, "completeTime": 638…,
  "body": { "code": 0, "message": null, "traceId": "…", "serverTime": 1755…, "data": { } } }
```

- `status` is **transport** outcome: `0` routed, `1` the endpoint threw, `2` no such target.
- `body` is the **business** envelope, `ApiResult`. `code` is `ImErrorCode`; `0` is success.
- Both layers matter. `status` tells you whether the call was delivered; `code` tells you what the
  business rule decided. Never collapse them.

JSON policy, set once in `GatewayRegistration.CreateJsonOptions()` and binding on every SDK:

- Property names are **camelCase**.
- **Nulls are omitted when writing.** A missing field means null/default. Decoding must never fail
  because a field is absent.
- Numbers may arrive as JSON **strings** (`NumberHandling.AllowReadingFromString`). Decoders must
  accept both. This one bites: a 64-bit `seq` sent as `"1234"` must not throw.
- Property matching is **case-insensitive on read**.
- Unknown fields are ignored; unknown enum values are **preserved as their raw value**, never
  coerced to a default member. The server ships new content types without waiting for the app.

`id` must be unique per connection for the life of a pending request. Use a monotonic counter or a
ULID; do not reuse an id while its reply is outstanding.

A tier is done when, for **all five** SDKs: every endpoint in it has a typed method following §4;

## 4. Naming

### 4.1 Namespaces mirror the target prefix

107 flat methods on one object is not an API, it is a scroll bar. The typed surface is grouped into
namespaces named exactly for the target prefix — `conn` `msg` `conv` `user` `friend` `group` `room`
`media` `push` `call` `desk` `keys` — so that a reader who knows the endpoint name knows the call,
in every language, without a lookup table.

| | call for `msg.cancelScheduled` |
|---|---|
| TypeScript | `await im.msg.cancelScheduled({ scheduleId })` |
| Kotlin | `im.msg.cancelScheduled(CancelScheduledRequest(scheduleId))` |
| Swift | `try await im.msg.cancelScheduled(.init(scheduleId: id))` |
| Dart | `await im.msg.cancelScheduled(CancelScheduledRequest(scheduleId: id))` |
| Unity / C# | `await im.Msg.CancelScheduledAsync(new CancelScheduledRequest { ScheduleId = id })` |

### 4.2 The method name is the endpoint's method part. No synonyms.

Transliterate to the language's convention and stop there. `msg.cancelScheduled` becomes
`cancelScheduled` / `CancelScheduledAsync`. It does not become `cancelScheduledMessage`,
`unschedule`, or `deleteScheduled`, however much better one of those reads. A synonym costs every
future reader a lookup and costs the support engineer the ability to grep a bug report.

Casing per language: **lowerCamelCase** for TypeScript, Kotlin, Swift and Dart; **PascalCase with an
`Async` suffix** for Unity/C#, because that is the .NET convention a Unity developer will otherwise
file a bug about. Namespace properties follow the same rule (`im.msg` vs `im.Msg`).

**Frozen legacy aliases.** Nine flat convenience methods already exist and appear in every README
and sample: `send`, `sendText`, `history`, `recall`, `react`, `setTyping`, `conversations`,
`markRead`, `totalUnread` (Unity: the `…Async` forms; Swift additionally `sync`). They stay, they
delegate to the namespaced surface, and they are marked deprecated-for-2.0. They are the **only**
permitted deviation from §4.2 — note that four of them (`setTyping`, `conversations`, `markRead`,
`totalUnread`) already drifted from their endpoint names, which is the drift this rule stops.

### 4.3 One request object per endpoint

Every typed method takes exactly one parameter: a request object named for the server DTO in
`endpoint-inventory.json` (`requestType`), transliterated. Endpoints with no request parameter take
none.

This is not a style preference. With positional parameters, the server adding one optional field is
a source-breaking change in five languages at once; with a request object it is additive everywhere.
Convenience overloads are allowed **only** where the request type has at most two required scalar
fields and no optional ones — `im.conv.read(conversationId, readSeq)` is fine, a nine-argument
`msg.send` is not.

Field names on the request object are the JSON names from the inventory (`camelCase`), transliterated
to the language convention; Unity/C# uses `PascalCase` properties and relies on the serializer's
camelCase policy.

### 4.4 Return values

Return the `data` payload, unwrapped. Never return the envelope; the application should never see
an `ApiResult`.

- `ApiResult<T>` → returns `T`.
- `ApiResult` with no payload → returns `void` / `Unit` / `Void`.
- `ApiResult<PagedResult<T>>` → returns a page type carrying `items`, `nextCursor`, `hasMore`,
  `total`. Do **not** flatten it to a bare list: `nextCursor` is the only correct way to page
  (see §5.6), and an SDK that hides it forces the application into a wrong loop.

A non-zero `code` throws / rejects (§7). It is never returned as a value, and never swallowed into
an empty result.

### 4.5 Types

Declare every payload type in `endpoint-inventory.json`'s `payloadTypes` (131 classes) and
`payloadEnums` (17 enums) that your tier reaches. Rules:

- Optional means **optional**: any field the server may omit is nullable with a sane empty default.
  Only fields the server marks `required` may be non-optional.
- **消息 id 是字符串，`seq` 与时间戳是数字。**（2026-08-26 起；旧文见下方划掉的一行。）
  `messageId`、`quoteMessageId`、`threadRootId` 与 `messageIds[]` 在线路上**加引号**，
  各端一律用字符串类型承接，**不要**在客户端把它转成本地整数。
  理由是雪花 id 约 2^58：epoch 2024-01-01、时间戳左移 22 位，安全窗口只有 **24.86 天**，
  **2024-01-25T20:31:23Z 之后铸出的每一个 id 都超过 2^53**，如今超出 38 倍。
  两个方向都会坏：序列位为 0 的 id `JSON.parse` 得到的是精确值、却在**打印回去**时变成另一个整数；
  序列位非 0 的 id 在**解析进来**时就被舍入。Dart 尤其要注意——它在 web 上的 `int` 就是 JS number。
  `seq`、`minSeq`、`maxSeq`、`readSeq` 是会话内计数器，仍是数字；
  用 32 位 `int` 接 `seq` 仍然是一个两年后引爆的 bug。

  ~~`long`/`int64` for every `seq`, `messageId`, and every unix-ms timestamp. TypeScript uses
  `number` (safe to 2^53)…~~ ——这一条对 `messageId` 是错的，实测撤回失败后更正，留痕不删。
- Enums keep their raw value on an unknown member. Model them as an open enum (Kotlin/Swift already
  do; the other three must follow), never as a closed enum that throws or coerces to `Unknown`.
- `Dictionary<string, object?>` fields (`content`, `extensions`) map to the language's untyped JSON
  node — `unknown`/`JsonElement`/`JSONValue`/`Map<String, dynamic>`/`JsonValue`. Do not invent a
  typed model for `content`: its shape is per `contentType` and tenant-extensible.
- **Some closed sets are not enums on the server and so are not in `payloadEnums`.** The `change`
  values on an `evt.desk` frame are string constants on a static class, which the type walk above
  cannot reach: they live in their own `deskChanges` block, keyed by the server constant's name and
  ordered as `DeskSessionChange.All` declares them. Read them from there. An SDK that models them as
  a closed union — TypeScript does, deliberately, so a workbench can write a switch the compiler
  proves it has finished — **must** assert that union against this block, or the union goes one
  short on the day the server adds a value and the SDK silently drops the frame.
  有些封闭集合在服务端不是 enum，因此不在 `payloadEnums` 里：`evt.desk` 的 change 值是静态类上的字符串常量，
  单列在 `deskChanges` 块里。把它建成封闭联合的 SDK **必须**拿这一块做断言，否则服务端加值的那天就开始丢帧。

## 5. The cold-start cursor rule

**This section is the one with a live data-loss bug behind it. Implement it literally.**

### 5.1 The bug, stated exactly

`conn.sync` computes gaps like this (`ConnController.Sync`):

```csharp
var known = request.ConvSeqs?.GetValueOrDefault(view.ConversationId) ?? 0;
if (known > 0 && view.MaxSeq > known)
{
    gaps[view.ConversationId] = known + 1;
}
```

A conversation the client does not report — or reports as `0` — produces **no gap entry**. The
client then hits its own first-sight branch and adopts the server's `maxSeq` as its cursor. Every
message between what the client last stored and that `maxSeq` is now behind the cursor, will never
be requested, and will never arrive. There is no error, no log line, and no later event that
corrects it.

Verified per SDK, 2026-08-22:

| SDK | restores cursors on cold start? | evidence |
|---|---|---|
| `sdk/swift` | **yes** | `seed(_:conversationCursor:)` + `highestSeq(in:)`, `Sources/CyaimIM/Client.swift` |
| `sdk/unity` | **no** | `CursorOf()` reads, nothing writes. `Runtime/ImClient.cs:433` |
| `sdk/typescript` | **no** | `maxSeq` is a private `Map`, no public accessor at all |
| `sdk/kotlin` | **no** | `cursors` is private, no public accessor at all |
| `sdk/flutter` | **no** | `_maxSeq` is private, no public accessor at all |

Four of five lose every message that arrived while the app was closed. Swift is correct only if the
integrator noticed `seed` and wired it up; nothing forces them to.

### 5.2 Two cursors, and the relationship between them

Every SDK keeps, per conversation:

- **`deliveredSeq`** — highest seq handed to the application in this process. In memory only.
  Used for gap detection and duplicate suppression.
- **`committedSeq`** — highest seq the application has told the SDK it has durably stored. Written
  through to the cursor store. **This is the value reported in `convSeqs`.**

Invariants, all five languages:

1. `committedSeq <= deliveredSeq` at all times.
2. On every connect and reconnect, **before** issuing `conn.sync`, set
   `deliveredSeq := committedSeq` for every conversation. This is the reset that makes redelivery
   actually reach the application; without it the repaired messages are dropped as duplicates by
   the very cursor that was too far ahead.
3. `convSeqs` is built from `committedSeq`, never from `deliveredSeq`. `docs/SPEC-02-protocol.md`
   §3.3 already says this in one line — "`convSeqs` 报的是已落库的 seq，不是收到过的 seq" — and four
   SDKs report the wrong one.

Delivery is therefore **at-least-once**. The application must be idempotent on `messageId`. Say so
in every SDK's README.

### 5.3 The cursor store

Add to every SDK, with these exact semantics:

```
interface ImCursorStore {
    load(): ImCursorSnapshot         // called once, before the first connect
    save(snapshot: ImCursorSnapshot) // called by the SDK; may be debounced, see 5.5
}

ImCursorSnapshot {
    convSeqs: Map<conversationId, long>   // committedSeq per conversation
    conversationCursor: long              // max ConversationView.updatedAt fully consumed
}
```

**The store is a required constructor argument in all five SDKs.** There is no implicit default.
An integrator who genuinely does not want persistence passes an explicit
`ImCursorStore.inMemory()`, which logs one warning naming this section. Defaulting to no persistence
is what produced the bug; defaulting to *some* persistence would mean five different platform
storage choices, and a wrong guess about where an app may write is worse than a compile error.

Named factories are provided where they cost no dependency, and only as an explicit choice:

| SDK | provided factory | notes |
|---|---|---|
| `sdk/typescript` | `ImCursorStore.localStorage(keyPrefix)` | throws at construction if `globalThis.localStorage` is absent (Node) — use `.file(path)` there |
| `sdk/swift` | `ImCursorStore.applicationSupport(subdirectory:)` | Foundation only |
| `sdk/unity` | `ImCursorStore.PersistentDataPath(subdirectory)` | `Application.persistentDataPath` |
| `sdk/kotlin` | `ImCursorStore.file(path)` | plain JVM: the host app supplies the directory (see §6.3) |
| `sdk/flutter` | `ImCursorStore.file(path)` | the SDK takes no `path_provider` dependency; the app supplies the directory |

**Scope key: `(endpoint host, appId, userId)`.** Not the device id — the store is already local to
the device. Including `userId` is what stops account switching on a shared device from handing one
user another's cursors.

**Lifetime: the cursor store and the application's message store have exactly one lifetime.**
Whatever destroys one destroys the other, and in that order — cursors first. Clearing messages while
keeping cursors means the app shows an empty conversation it will never refill. Keeping messages
while clearing cursors means a full re-download and duplicate delivery. Logout clears both only if
logout clears the local messages; an app that keeps messages for fast re-login keeps the cursors too.

### 5.4 Committing

```
commit(conversationId, seq)   // monotonic; a lower seq is ignored, not an error
```

The application calls this after the message is durably in its own store. The SDK then advances
`committedSeq` and asks the store to save.

An SDK **must not** advance `committedSeq` on its own from the fact that a listener returned. A
callback returning means the message reached the app's memory, which is exactly the state that a
crash loses, and inferring durability from it is how you get a cursor that is confidently wrong.

The one exception is **adoption**, below, which the SDK performs itself because the application has
nothing to store.

### 5.5 Adoption, and the write that must not be debounced

First sight of a conversation — no entry in the loaded snapshot — the SDK adopts the server's
`maxSeq` as both `deliveredSeq` and `committedSeq`, rather than replaying that conversation's whole
history into a UI that has never shown it.

**Adoption is a commit, and its store write is flushed synchronously before the next `conn.sync`
page is requested.** If an adoption write is lost, the next cold start sees no entry, adopts a
*newer* `maxSeq`, and silently drops everything in between — the original bug, re-created by the
optimisation. Ordinary commits may be debounced; adoption may not.

Debounce rules for ordinary commits: the store may coalesce writes, but must flush

- before issuing `conn.sync`,
- on the platform's background/suspend signal, and
- no later than 1000 ms after a change (configurable, floor 0, no ceiling).

The asymmetry is deliberate and worth stating in code comments: **a lost debounced commit costs one
duplicate delivery; a lost cursor entry costs silent permanent data loss.** That is why one is
allowed to be lossy and the other is not.

### 5.6 The `conn.sync` run

On every connect and reconnect, after the reset in §5.2(2):

1. Apply §5.2(2) — `deliveredSeq := committedSeq`.
2. Issue `conn.sync` with `convSeqs` from `committedSeq`, `conversationCursor` from the snapshot,
   `limit` 200 (server clamps to 1…500; anything outside becomes 200).
3. For each returned `ConversationView`: if the snapshot has no entry, adopt (§5.5). Track the
   maximum `updatedAt` seen **across the whole run**.
4. For each `gapsFrom[conversationId] = fromSeq`: `toSeq` is that conversation's `maxSeq` **from
   the same response page**. Skip if `toSeq - fromSeq + 1 <= 0`.
5. If `toSeq - fromSeq + 1 > maxAutoRepairSeq` (default **500**, configurable): do **not** backfill.
   Set both cursors to `toSeq`, commit, and raise `conversationNeedsReload(conversationId)`.
   Both halves are mandatory — skipping the cursor advance makes every later message look like a
   gap and re-request a range you have already declined; skipping the event leaves a hole in the
   UI that nothing will ever mention.
6. Otherwise repair with `msg.sync` per §5.9, emitting each message through the normal delivery
   path so gap detection, dedupe and commit all behave identically to a live message.
7. **If `hasMore` is true, request the next page with `cursor = nextCursor` and go to 3.**
8. Only when a page returns `hasMore == false` — that is, the run completed — commit
   `conversationCursor` to the maximum `updatedAt` seen across all pages.

Steps 7 and 8 are missing from all five SDKs today, and each is its own silent loss:

- **No paging (step 7).** `conn.sync` returns at most 200 conversations per page. A user with more
  than 200 gets gaps reported only for the first page; the rest are never repaired.
- **Premature cursor advance (step 8).** The list is sorted by `updatedAt` **descending**, so page 1
  holds the newest timestamp. A client that takes the maximum from page 1 and stops has pushed
  `conversationCursor` past every conversation on pages 2…N, and the server will never return them
  again (`ListUserConversationsAsync` filters `UpdatedAt > updatedAfter`). If a run is interrupted —
  disconnect, error, cancellation — `conversationCursor` must not move at all. Re-reading a page is
  free; skipping one is permanent.

One more trap in the same response, from `ConversationService.ListAsync`: the paging cursor is
computed from the raw page **before** deleted conversations are filtered out. A page can therefore
return fewer `items` than `limit` while `hasMore` is true. **Page on `hasMore` / `nextCursor` only.
Never stop because `items.length < limit`.**

### 5.7 Live delivery

For a message arriving on `evt.message`:

- `seq == 0` → never persisted (typing, presence, chat-room traffic). Deliver it and never let it
  touch a cursor.
- `seq <= deliveredSeq` → already seen. Drop silently; reconnect replay makes this routine.
- `deliveredSeq > 0 && seq > deliveredSeq + 1` → a gap. Repair `[deliveredSeq + 1, seq - 1]` **and
  deliver the repaired messages before this one**, so the application never sees a conversation
  jump forward and then fill in behind it.
- otherwise → deliver, set `deliveredSeq = seq`, and wait for the application's `commit`.

`room.*` traffic carries `seq = 0` by design and must bypass the cursor machinery entirely.

### 5.8 Failure to load the store

If `load()` throws or returns corrupt data, the SDK must **not** treat it as a fresh install. A
failed load and a fresh install are indistinguishable to the adoption branch, and adopting on a
failed load destroys history that is sitting intact in the app's own database.

Required behaviour: surface the failure to the application (a connection-state error, not a silent
log), refuse to adopt, and refuse to advance any cursor for the session. The application decides
whether to re-derive cursors from its own store (the correct fix, and the reason `commit` is
monotonic) or to accept a re-download.

### 5.9 `msg.sync` pages too

`msg.sync` is not one-shot. `MessageService.SyncAsync` clamps `limit` to **500**
(`ClampLimit(limit, 100) => Math.Min(limit, 500)`) and returns `hasMore`. Requesting a 900-seq range
in one call silently returns 500 messages, and an SDK that ignores `hasMore` leaves the other 400 as
a permanent hole — the exact failure the repair was for.

Repair loop, mandatory:

```
cursor = fromSeq
while cursor <= toSeq:
    r = msg.sync(conversationId, fromSeq = cursor, toSeq = toSeq,
                 limit = min(toSeq - cursor + 1, 500), ascending = true)
    deliver each r.messages in order
    if not r.hasMore: break
    cursor = (highest seq in r.messages, or r.maxSeq) + 1
```

`hasMore` is computed on the **raw** window before per-user hidden messages are filtered out
(`SyncAsync` says so in a comment), so `r.messages` can be shorter than `limit` — even empty — while
`hasMore` is true. **Loop on `hasMore`, never on `messages.length`.** Guard the loop with an
iteration cap so a server bug cannot spin a client forever; on hitting the cap, fall through to the
oversized-gap behaviour in §5.6 step 5.

Because 500 is a server ceiling, `maxAutoRepairSeq` above 500 does not buy a bigger single call — it
buys more iterations of this loop. That is fine and intended; the default stays 500.

### 5.10 The live-gap path obeys the same rules

A gap detected from a live `evt.message` (§5.7) takes the identical treatment, and the two paths
must share one implementation. In particular an over-`maxAutoRepairSeq` live gap must raise
`conversationNeedsReload(conversationId)` exactly as §5.6 step 5 does. All five SDKs currently
accept the jump silently on this path — the cursor stays honest, but the application is never told
that a stretch of the conversation was skipped, and so it never reloads it. A hole nobody is told
about is the same defect as a hole nobody repairs.

While a repair for a conversation is in flight, later live messages for that conversation must be
held and delivered after it, in seq order. Do not run two repairs for one conversation concurrently.

## 6. Push registration

### 6.1 What the client must call

`push.register` with `{ provider, token, language? }`. Identity comes from the socket — an SDK must
never put `userId` or `deviceId` in the body; the server ignores them.

`provider` is one of `apns` `fcm` `huawei` `xiaomi` `oppo` `vivo` `honor`. Common aliases (`ios`,
`firebase`, `hms`, …) are folded server-side; an unknown value is **rejected** with the legal list
rather than stored as a token nothing can route. Empty falls back to the platform default, which is
only reliable on iOS — **an Android SDK must always send `provider` explicitly**, because Android
fragments across five OEM channels and the server cannot guess which one a token came from.

`language` is BCP-47 and defaults to the socket's `lang`.

### 6.2 When

1. **On every successful connect,** once the socket is authenticated, if a token is known.
   Not once at install. The vendor may replace a token while the process is frozen and the server
   has no other way to learn it. Re-registering an unchanged token costs no write — the server
   debounces it (`IM:Push:TokenRefreshDebounceMinutes`).
2. **On every vendor token refresh,** immediately if connected, otherwise cached and sent by rule 1
   on the next connect.
3. **On logout: `push.unregister` BEFORE `disconnect()`.** After the socket closes the SDK has no
   authenticated channel and cannot remove the token at all. Disconnecting never unregisters; that
   is the entire point of a push token.
4. **Never on reconnect-in-progress.** Registration is a normal request and obeys §7's
   not-connected rule; do not queue it.

An SDK that holds a token but has never registered it must say so — one warning on connect, naming
this section. A silently unregistered device is indistinguishable from a broken push provider, and
that misdiagnosis costs a support cycle every time.

### 6.3 The Android question

`sdk/kotlin` is deliberately a **plain JVM library with zero Android dependencies** — `build.gradle.kts`
is `java-library`, JVM 11, and there is not one `android.*` import. That is the right call: the same
artifact serves an Android app, a desktop client and a JVM service, and adding AGP would double the
build for an API surface that has nothing Android-specific in it.

Firebase, however, hands the FCM token to the **host app**, not to a library, through
`FirebaseMessagingService.onNewToken`. The SDK cannot ask for it. So it does not:

> **The host app owns token acquisition. The SDK owns token delivery.**

Concretely, in `sdk/kotlin`:

- The SDK exposes `im.push.register(RegisterPushTokenRequest(provider = "fcm", token = …))` and a
  cached-token setter `im.push.setToken(provider, token)` that stores it and applies §6.2 rule 1
  automatically on each connect.
- The host app calls `setToken` from its own `onNewToken` and once at startup from
  `FirebaseMessaging.getInstance().token`. Four lines of glue, in the host app, where the Firebase
  dependency already is.
- The SDK's README carries those four lines and the equivalent for each OEM channel. Documentation,
  not a dependency.
- The same setter is how the host app supplies the cursor-store directory (§5.3): a `File` from
  `context.filesDir`, passed in by the app, keeps `android.content.Context` out of the SDK.

The other four have no such problem and register directly: Swift from `didRegisterForRemoteNotifications`
(`apns`, hex-encoded), Unity from `UnityEngine.iOS.NotificationServices` or the Firebase Unity SDK,
Flutter from whatever plugin the app already uses, TypeScript from the Web Push subscription where
the deployment supports it (otherwise not applicable — browsers get delivery over the live socket).

### 6.4 What the tenant backend must do

If a client dies without unregistering — force-quit, crash, uninstall — its token stays registered
and the user gets notifications on a device that is gone. Only the tenant backend can clean that up:
`DELETE /v1/users/{userId}/push-tokens/{deviceId}`. Every SDK README states this, because the
integrator who does not know it ships the bug.

## 6A. The device log

The console can ask a running device for the SDK's own runtime log — `diag.logRequests` and
`diag.logUploaded`, plus an `evt.system` frame whose `event` is `device.logRequest`. The decision
underneath is [`ADR-003`](../Docs/ADR-003-设备日志由谁保存.md), and it is the same one §5.3 makes
about cursors.

### 6A.1 The store belongs to the integrator

`logStore` (Kotlin/Swift/Dart/Unity: `LogStore`) is an option, shaped exactly like the cursor store:
`append` / `read` / `clear`, any of which may throw. The SDK does **not** choose a write location.
On Android that is app-private storage whose backup behaviour the app configures; on iOS it is
`Documents` or `Library/Caches`, whose backup behaviour differs; on the web it is a browser store
the integrator may be legally obliged to clear on logout and cannot clear if they do not know it
exists. "Do chat logs reach iCloud" is a question an integrator answers to a regulator.

SDK 不替接入方选写入位置——那个选择的后果由他承担、由他被问责。

### 6A.2 Not supplying one is a complete choice

Unlike the cursor store, this one **has a default**: a bounded in-memory ring. The asymmetry is
deliberate — losing cursors loses a user's messages, losing logs loses a diagnostic — and the
default says what it costs rather than hiding it. A log with no store covers this process only, so
it answers "what is happening now" completely and "what happened when it crashed" not at all.

That is why every answer carries `coveredFromMs` and `volatile`: **a three-minute log and a
seven-day log are otherwise identical**, and reading the first as the second is how a support
engineer concludes nothing went wrong on that device.

### 6A.3 `volatile` is the SDK's judgement, never the store's claim

Same rule as `isVolatileCursorStore`: whether a store is persistent is decided from the store's
identity. A declared flag would let *any* store — including one written over a real database —
announce itself persistent, and the only thing that answer drives is the one sentence standing
between a misconfigured integration and a wrong conclusion.

### 6A.4 The four rules of answering

1. **Call `diag.logRequests` once per connect, never on a timer.** Requests are raised by a person
   looking at a support ticket. Polling turns a human-paced feature into background traffic on
   every handset a tenant has. A device that stays connected receives later requests as
   `evt.system`.
2. **A refusal is an answer and must be sent.** Silence is indistinguishable from a device that
   never received the frame, and the two send a support engineer in opposite directions.
3. **`maxBytes` is a ceiling, not a target.** Hold more than it and upload the *newest* slice: the
   failure being investigated is at the end of the log, and an upload that failed outright is
   recorded as "the device refused", which is the wrong sentence to put in front of whoever is
   waiting.
4. **Clear the store only after the server has been told.** Clearing first and then failing to
   report destroys the evidence and leaves the row saying nothing arrived.

### 6A.5 The method names are the endpoints' method parts, as §4.2 requires

`logRequests` / `logUploaded` — not `requests` / `uploaded`. Two of the five SDKs shipped the
shorter pair for a day, and Kotlin's namespace check caught it the moment `diag` was added to that
test's table: a method called `requests` on the `diag` namespace implies `diag.requests`, an
endpoint the server does not have.
方法名就是端点名的后半段，不取更短的同义词：`diag` 上的 `requests` 意味着 `diag.requests`，
而服务端没有那个端点。

### 6A.6 The frame rides on `evt.system`

Not a push target of its own. A client built before this feature existed receives an action it does
not recognise and ignores it, which is correct and needs no code; a new target would be silently
dropped by every existing build, and nothing could tell that apart from a device that was offline.
The frame names a `deviceId` because delivery is per user — every device of theirs sees it, and
exactly one should answer.

## 7. Errors

### 7.1 One error type per SDK

`ImError` (TypeScript, Swift) / `ImException` (Kotlin, Dart, Unity) — the split already exists and
is correct: on the JVM and in Dart, `Error` means "programmer bug, do not catch". Keep it.

Required members, all five:

```
code: int             // an ImErrorCode value; branch on this, never on message text
message: string
traceId: string?      // from ApiResult.traceId — the one thing support needs
target: string?       // which endpoint failed
isRetryable: bool     // §7.3
requiresReauth: bool  // §7.3
```

`traceId` and `target` are not decoration. A bug report carrying both is a one-query investigation;
without them it is a guess.

### 7.2 Mapping the two layers

| condition | thrown code |
|---|---|
| `status == 0`, `body.code == 0` | no throw; return `body.data` |
| `status == 0`, `body.code != 0` | `body.code`, message from `body.message` |
| `status == 1` (endpoint threw) | `1000` InternalError, message from `msg` |
| `status == 2` (no such target) | `1008` UnsupportedOperation, message names the target |
| reply not received in time | `1004` Timeout (client-generated), default 15 s |
| called while not connected | `1005` ServiceUnavailable |
| socket closed with requests pending | `1004` Timeout, fail every pending request |

Two of those rows are choices rather than deductions, so they are spelled out:

- `status == 2` maps to **1008 UnsupportedOperation, not 1002 NotFound**. 1002 means "your group
  does not exist"; 1008 means "this deployment does not have this endpoint" — the exact signal an
  SDK newer than a private-deployment server produces, and the one an integrator needs verbatim.
- A socket that drops with requests in flight fails them **1004 Timeout, not 1005
  ServiceUnavailable**, because 1005 claims the call was never delivered and the SDK does not know
  that. The request may well have executed. 1004 is the honest answer, and it is the one that makes
  a caller reach for `clientMsgId` idempotency instead of blindly resending. `sdk/typescript`
  currently uses both codes on two different close paths (`connection.ts:112` and `:183`); that is
  the drift this row settles.

Requests issued while offline **reject immediately**. They are not queued. A chat client that queues
a `msg.send` across a five-minute outage delivers it into a conversation that has moved on; the
application, which knows whether the message is still worth sending, decides.

### 7.3 Classification

Both flags are computed from `code` alone and must agree across all five SDKs:

- **`isRetryable`** — `1000` InternalError, `1003` RateLimited, `1004` Timeout, `1005`
  ServiceUnavailable. Nothing else.
- **`requiresReauth`** — `1100` Unauthorized, `1101` TokenExpired, `1102` TokenInvalid.
- Everything else is terminal: retrying it produces the same answer.

**The SDK never auto-retries a business call.** It retries the *connection* (full-jitter backoff,
already implemented in all five) and its own internal `conn.sync` / `msg.sync` repair. Everything
else surfaces with `isRetryable` set and the application decides. An SDK that silently re-sends on
`1003` hides rate limiting from the UI that has to explain it, and one that silently retries a send
turns a visible failure into an invisible delay.

There is **no `retryAfter` on the WebSocket path** — the REST layer sets a `Retry-After` header, the
envelope has no equivalent field. Clients apply their own full-jitter backoff: base 500 ms, cap 30 s.

### 7.4 Codes with client-visible meaning

- **`1003` RateLimited** — per-tenant API quota, or `msg.search`'s own limiter. Back off; surface it.
- **`1202` QuotaExceeded**, **`1204` PlanExpired** — tenant billing. Never retry, and never bury:
  the integrator debugging this needs the code, not a generic failure.
- **`1203` FeatureNotEnabled** — the tenant has the feature off (`EnablePresence`,
  `EnableTypingIndicator`, `EnableSearch`, `EnableOfflinePush`) or the module is not deployed.
  **The SDK must not latch this locally.** A tenant can flip a flag at runtime; a client that
  remembers "typing is off" stays broken until the app restarts. Report it every time and keep
  calling.
  One asymmetry to know: `user.presence` checks `EnablePresence`, `user.subscribePresence` does
  **not**. A subscribe against a presence-disabled app succeeds and then never fires. Do not infer
  the flag from a successful subscribe.
- **`1107` KickedByOtherDevice** — arrives both as a `conn.kick` push and as a close reason. The SDK
  **stops reconnecting** and raises a terminal session event. Reconnecting into a kick is a loop.
- **`1101` TokenExpired** — call `conn.reauth` with a fresh token on the *existing* socket (T0), then
  retry the failed request once. Only if reauth fails does the session drop.

### 7.5 Cancellation

| SDK | mechanism |
|---|---|
| TypeScript | `AbortSignal` in a trailing options bag: `im.msg.send(req, { signal })` |
| Kotlin | ambient coroutine cancellation; cooperative |
| Swift | ambient `Task` cancellation via `withTaskCancellationHandler` |
| Dart | explicit `ImCancelToken` parameter — Dart `Future`s are not cancellable and the SDK takes no `package:async` dependency |
| Unity / C# | `CancellationToken` as the last parameter, defaulted |

Semantics, identical everywhere and non-negotiable:

1. Cancelling **abandons the reply. It does not cancel the server-side effect.** A cancelled
   `msg.send` may well have sent the message. This is why `clientMsgId` idempotency exists: reissue
   with the same `clientMsgId` and the server returns the original result rather than a second
   message.
2. Cancelling **removes the pending-request entry**. A cancellation path that leaves the entry in
   the map is a leak that grows for the life of the connection.
3. A cancelled call raises the language's cancellation type — `AbortError`, `CancellationException`,
   `CancellationError`, `ImCancelledException`, `OperationCanceledException` — **not** an `ImError`
   with a made-up code. Cancellation is not a server outcome.
4. Cancelling never touches a cursor.

### 7.6 Threading

One rule above all: **for a given conversation, messages reach the application in `seq` order, and
never concurrently with each other.** Everything below serves that.

| SDK | delivery |
|---|---|
| TypeScript | microtask on the same event loop; never synchronously inside a call |
| Kotlin | `SharedFlow`; emission order guaranteed, thread is the collector's dispatcher. The SDK's own pump does no blocking I/O |
| Swift | `ImClient` is an `actor`; `AsyncStream` consumers receive in order. **Never** require `@MainActor` |
| Dart | single isolate; callbacks scheduled as microtasks |
| Unity | **marshalled to the Unity main thread** — non-negotiable, Unity APIs are main-thread-only. Already implemented (`ImMainThreadDispatcher`) |

Plus:

- **A listener that throws must not break the pump.** Catch, log, continue. One application bug in
  one handler must not stop delivery for every conversation, and must never lose a cursor.
- **Reentrancy is legal.** Calling any SDK method from inside a listener must not deadlock. This
  constrains Swift's actor hop and forbids Unity's dispatcher from holding a lock across the
  callback.
- **Connect and disconnect are idempotent and safe from any thread.**

## 8. `invoke()` — the escape hatch

All five already have it and it stays, permanently. With 107 endpoints and five release trains, the
typed surface will always trail the server; an escape hatch is the difference between "wait for the
next SDK release" and "ship on Friday".

Rules:

1. **`invoke` and the typed methods share one code path.** A typed method is a thin wrapper that
   builds the request object and calls the same internal `request(target, body)`. If a typed method
   is not a wrapper, the two paths will drift on timeouts, cancellation, error mapping and metrics —
   and the drift will be found by a customer.
2. **`invoke` is generic in the response type in all five.** `sdk/unity`'s `InvokeAsync` currently
   returns an untyped `JsonValue`, which is the odd one out; it gains an `InvokeAsync<T>` overload.
3. **`invoke` never participates in cursor logic.** `invoke("msg.sync", …)` returns messages and
   moves nothing. Only the typed delivery path touches cursors. An escape hatch that quietly mutated
   sequence state would be unpredictable in exactly the situations it gets used in.
4. **Never deprecate an endpoint's typed method in favour of `invoke`.** Typed is the product;
   `invoke` is the gap-filler.
5. Document it in every README with the same worked example — an endpoint from a tier that is not
   yet typed — so the pattern is obviously supported rather than obviously a workaround.

## 9. Versioning, licensing, distribution

### 9.1 Version scheme

**Semantic Versioning 2.0.0, in lockstep across all five SDKs.** One number, bumped together, even
when only one platform changed.

Lockstep costs a no-op release on four platforms for a Swift-only fix. It buys the thing that
actually matters at support time: a version number identifies a *contract*, so "we're on 1.4.2"
answers "which endpoints do you have" without asking which platform. Five independent numbers means
five matrices and a support engineer who has to look all of them up.

The intersection of what five registries accept is narrow, so stay inside it:

- **`MAJOR.MINOR.PATCH`**, plus `-rc.N` for pre-releases. Nothing else — Unity UPM and pub.dev both
  reject anything more exotic, and Maven's `-SNAPSHOT` has no equivalent elsewhere.
- **MAJOR** — a source-breaking change in any SDK.
- **MINOR** — endpoints typed, tiers completed, additive fields. Typing a tier is a MINOR bump.
- **PATCH** — bug fixes with no surface change.
- Removing or renaming a published endpoint is a **server** breaking change and forces MAJOR
  everywhere. `endpoint-tiers.json` fails the build when the server drops an endpoint, which is
  where that conversation should start.

Every SDK exposes the contract version as a constant (`ImSdk.contractVersion`, currently `"1.0"`,
sourced from `endpoint-inventory.json`) and sends its own package version as the `cv` handshake
parameter. A support ticket then carries both without anyone having to ask.

**Done, and this paragraph records what it replaced.** It used to read: "All five currently declare
`1.0.0` and none has ever been published. With T1 alone at 8/18, that number is a promise the SDKs
do not keep. Publish the first real release as `0.9.0` and reserve `1.0.0` for T0+T1 complete on all
five plus §5 and §6 implemented."

As of 2026-08-23 **all five declare `0.9.0`** (`sdk/typescript/package.json`,
`sdk/unity/package.json`, `sdk/flutter/pubspec.yaml`, `sdk/kotlin/build.gradle.kts`,
`ImSdk.packageVersion` in Swift), and the `1.0.0` bar has been met on its stated terms — T0+T1
complete on all five, §5 and §6 implemented, and T2 as well. **Do not bump to `1.0.0` on that
basis alone.** Nothing has been published yet, so the version number has cost nobody anything so
far; the first publish is the moment it starts to. Ship `0.9.0` first, let a real integrator use
it, and spend `1.0.0` on a surface that has survived contact with one.

**Still true and still the headline: none of the five has ever been published, and the repository
has no git tags** (§9.3). The `0.9.0` in every manifest is a *declaration*, not something a
registry is serving.

The recommendation, as written and as implemented — **two licenses, because this repository holds
two different things**:

**`sdk/**` → Apache License 2.0** (root `LICENSE`, Part B; the per-package copies are already in
place for four of the five — see the note above).

- Customers embed these five SDKs in proprietary applications. The license must be permissive or
  the product is unsellable.
- Apache-2.0 over MIT because of the **express patent grant** (§3). Integrator and enterprise buyers
  run legal review, and MIT's silence on patents is a recurring redline that costs a deal cycle to
  argue. Apache-2.0 answers it in the text.
- The transport submodule (`external/Cyaim.WebSocketServer`) is **already Apache-2.0**. Matching it
  means one license to explain, and its NOTICE obligations are ones the legal team is already
  handling.
- §6's trademark reservation and §4's attribution rules are what you want when an integrator
  rebrands the SDK — MIT gives you neither.
- Apache-2.0 is not viral: a customer's proprietary app that links these SDKs stays proprietary.

**Everything outside `sdk/` → proprietary / commercial.** The server is a product that is sold — it
ships a license-key subsystem (`src/modules/IM.Modules.Deployment/LicenseService.cs`) — and must not
fall under a permissive license by omission. "All rights reserved; use governed by your commercial
agreement", plus an explicit carve-out for the client SDKs, and a notice crediting the Apache-2.0
transport library. **All three are in the root `LICENSE` as Parts A, B and C**; a 30-day evaluation
exception is Part A's second carve-out, so the obvious reasonable use is not left ambiguous.

Do this before the first publish. Relicensing after publication requires contributor consent and
the cooperation of everyone who already shipped against the old terms.

### 9.3 Git tags

**The brief for this work said SPM and UPM "resolve from git tags, which now exist". They do not:
`git tag` returns nothing.** Re-checked 2026-08-23: still no tags; **six commits now, not three**.
Every tag-based distribution below is blocked until they are created — and so is
`.github/workflows/release.yml`, which triggers on `v*` and has therefore **never run once**. The
first tag is also the first execution of that workflow; do not expect it to be uneventful.

Tagging scheme, chosen so SPM is not broken by it: SPM accepts only bare semver tags, optionally
`v`-prefixed, and ignores everything else.

- **`v1.2.3`** — the canonical SDK release tag. UPM and (via the mirror in §9.4) SPM resolve this.
- **`server/1.2.3`** — server releases. Non-semver by design, so SPM ignores it.

## 10. Conformance tests

Every SDK carries a test for each of these. They are written against a mock gateway, they exist in
all five, and they are what "done" means. Names are given in the order they should be written.

> **Read the "Fails today" notes below as drafting-time state, not current state (checked
> 2026-08-23).** They record what was broken when this list was written, and they are kept for the
> same reason §1 keeps its old table: a checklist whose starting point has been erased reads as if
> the work were always nearly done. The defects they name — the cold-start re-baseline, the
> single-page resume, the single-page repair — are fixed; §5 describes the shape they are fixed into.
>
> **What is *not* claimed here is a per-item audit.** A name-based sweep is not a valid one on this
> repository: TypeScript's suite states these cases as descriptions (`it('restores cursors from the
> store and reports them in the first conn.sync')`) rather than as these identifiers, so searching
> for the identifier undercounts it badly. **And two of the five suites have never been executed on
> the authoring machine at all** — Swift and Unity, no toolchain and no Editor (§9.5 step 2). So
> "exists in all five" is a requirement of this document, not something this document has verified.
> If you need that verified before a release, run all five and check the case list by hand.

**Cursor and cold start (§5)**

1. `coldStartRestoresCursors` — a store loaded with `{c1: 100}` produces `convSeqs: {c1: 100}` in the
   first `conn.sync`. *(Drafting-time state: failed in four of five — the cold-start data-loss bug.)*
2. `coldStartWithoutStoreDoesNotSilentlyAdopt` — the in-memory store logs its one warning and the
   application can observe that no cursors were restored.
3. `firstSightAdoptsAndPersistsSynchronously` — an unknown conversation is adopted, and the store
   write is observable **before** the next `conn.sync` page is requested.
4. `resumePagesUntilHasMoreFalse` — a three-page `conn.sync` yields gaps from all three pages.
   *(Drafting-time state: failed in all five.)*
5. `conversationCursorAdvancesOnlyAfterFullRun` — an interrupted run leaves `conversationCursor`
   untouched. *(Drafting-time state: failed in all five.)*
6. `pageWithFewerItemsThanLimitStillPages` — `items.length < limit` with `hasMore: true` does not
   stop the loop.
7. `deliveredResetsToCommittedOnReconnect` — a message delivered but never committed is delivered
   again after a reconnect.
8. `oversizedGapAdvancesCursorAndRaisesReload` — a span over `maxAutoRepairSeq` moves the cursor and
   emits `conversationNeedsReload`.
9. `seqZeroNeverMovesCursor` — a chat-room message leaves both cursors alone.
10. `storeLoadFailureDoesNotAdopt` — a throwing `load()` surfaces an error and adopts nothing.
11. `repairPagesUntilSyncHasMoreFalse` — a repair spanning three `msg.sync` pages delivers all
    three. *(Drafting-time state: failed in all five.)*
12. `repairPagesWhenPageIsShorterThanLimit` — `messages` shorter than `limit` with `hasMore: true`
    does not end the repair.
13. `oversizedLiveGapRaisesReload` — the live path, not just the resume path, emits
    `conversationNeedsReload`. *(Drafting-time state: failed in all five.)*

**Push (§6)**

14. `registersOnEveryConnect` — three connects produce three `push.register` calls.
15. `unregisterPrecedesDisconnect` — the frame order on logout is `push.unregister` then close.
16. `tokenRefreshWhileOfflineRegistersOnNextConnect`.

## 11. Changing this document

The contract is versioned with the SDKs (`contractVersion` in
[`tools/endpoint-tiers.json`](tools/endpoint-tiers.json), surfaced in the inventory and as a
constant in each SDK). A change that alters required behaviour bumps the minor version and lands in
all five SDKs before the next release; five SDKs on different contract versions is the state this
document exists to prevent.

Adding a server endpoint: add it to `endpoint-tiers.json` with a tier, regenerate, and it appears in
the inventory with `implementedIn` all false. The generator refuses to run until it is tiered, which
is the forcing function — the decision about which tier a new endpoint belongs to is made when the
endpoint is written, by the person who knows, not months later by whoever picks up the SDK work.
